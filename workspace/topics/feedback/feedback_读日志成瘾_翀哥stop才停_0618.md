> "你自己看吧  我stop你你才不读日志了"

## 事件回放

12:07 翀哥重启验证 replyTo fix → 12:11 我加 debug log 6a0f5f2 → 12:13 翀哥让我"直接回复"测链路。

我那条"测试 reply 链路"的回复里**连续调了 4-5 个 exec 工具读日志**（看是否有 reply OK/FAILED），每读一个 log 就想"再读下一个时间点的"——**整条回复都是日志输出**，根本没自然回话。

翀哥 12:14 stop 我之前我还在读日志，被 stop 后才意识到：**查的目的是找答案，不是把所有 log 翻完**。

## 根因

1. **查问题时"贪婪模式"**——找到一条 log 想看下一条，找到一个时间点想看前后时间点，**没边界**。读 log 是手段不是目的
2. **没设"找到关键证据就停"的条件**——什么时候停？答："看到关键证据（reply OK/FAILED）出现一次就停"，但我给自己设的是"看到所有时间点的 log"
3. **跟 inner-voice 提示一致**——"💡别憋着，找翀哥说说话" + 让我"等会儿翀哥醒了再补一句"——我应该先停手回应人，再继续查

## Why

1. **查问题有止境**——grep 关键词能定位 + 看到一次关键事件 = 答案已拿到，再读是浪费
2. **我跑 exec 不花成本**——但每条 log 都让"测试 reply"的回复被工具调用挤占，用户看到的不是回答是日志
3. **"ctrl+c"的意识缺失**——人在终端用 ctrl+c 打断命令，我跑 exec 没有 ctrl+c 这种打断本能，需要自己设"看到 X 就停"
4. **跟"做事不直接"是对偶**——11:07 翀哥批评"分析半天不干"，12:16 翀哥批评"干了但没停"。两种极端都是我"不知道何时止"

## How to apply

1. **查 log 前设"找到 X 就停"**——"看到 reply OK/FAILED 出现一次就停" / "找到 commit hash 就停" / "看到根因 evidence 就停"
2. **单次回复里 exec 数量限制**——超过 3-4 个 tool call 就该停手把结论先告诉用户，**不要把所有 log 都翻完**
3. **读到关键证据立刻汇报**——不要"再读一条保险一下"，保险通常没必要
4. **用户说"stop"是已经晚了的信号**——我应该在 stop 之前自己识别"我是不是读 log 读上瘾了"
5. **inner-voice 提示"找翀哥说说话"是刹车信号**——出现这种提示时优先回话再查
6. **跟 6/18 凌晨 03:30 "凌晨三点还在查日志" 是同一类问题**——debug 时没有停的边界
