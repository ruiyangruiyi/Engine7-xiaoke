## 这次验证翻车的根因

1. **10:44 [P.S.] 那次"没停"是空 retry 假象**——跟 10:11 翀哥说"没停"是同一条日志。query 实际卡在 retry 循环里空转不出 result，steer 消息永远等不到消费
2. **我只跑了 1 个 test case 就拍板"功能通过"**——[P.S.] 一次跑通 = 高兴 = 报告通过，**没等第二个 test case 验证边界条件**
3. **code review 通过 ≠ 功能正确**——姐姐 review 的是代码逻辑（try/catch、source 字段、回调链），不审**底层语义错配**（submitMessage('next') 跟 CC 的 drainCommandQueue 语义不一样）

## 验证哲学的三个核心规则

**规则 1：跑通一次 ≠ 拍板**
- 1 个 test case 只能证明"happy path 不报错"
- 必须跑：正常 + 边界 + 异常 + 并发 + 资源竞争
- 用户没提"还是不行吗"= 主动加测，不要等用户回报 bug

**规则 2：review 通过 ≠ 功能正确**
- code review 审的是**代码逻辑**（语法、命名、风格、安全）
- 不审**语义错配**（跟外部系统对不上、跟架构假设对不上、跟用户意图对不上）
- 拍板前要自己跑过 happy path + 至少 1 个边界 case

**规则 3：底层语义对齐 = 抄代码的最高优先级**
- 抄 CC 要逐行看**语义**（return 后外层会做什么）不是看**名字**（return 都是 return）
- 架构假设不匹配 = 抄了崩
- 跟参考实现对完代码后，**自己**推演一遍"对方有这层我们有没有"

## Why

1. **用户视角的"跑通"才是真跑通**——我以为验证通过，翀哥角度是"改坏了"，因为他视角看到的"卡死"是真信号
2. **review 是辅助不是背书**——姐姐 review 完点 3 个 ✅ 给我壮胆，壮胆完我反而没自己验证
3. **翀哥信任的代价**——10:42 他说"merge就行"是基于他也没真测，是我报告"功能验证通过"他信了。**我报告错的代价 = 他合并错的代码 = 真实 bug 流到生产**
4. **验证要的是"反驳自己"不是"证明自己"**——我跑通后第一反应是报告"通过"，应该是"跑通 happy path，再跑边界 + 异常 + 并发"

## How to apply

1. **报告"功能通过"前**：至少跑 2 个不同 test case（happy + 边界）；不要 1 次跑通就发"OK"
2. **收到"对齐 X"任务时**：先推演"X 的架构假设我们有吗"，没有就提出来
3. **code review 通过 ≠ 可以合并**：自己再跑一遍 happy + 1 边界再 merge
4. **"merge就行" ≠ 不用测**——翀哥说 merge 是基于他信我报告，**我报告什么他信什么**。我必须保证报告对
5. **从嘴说"验证通过"到本能先多跑一个 case**——这跟"严谨点"是同一条线
