## 6/18 11:32 翀哥原话

> "我觉得是这样  1. 你打日志看下  提示词有没有在合适的地方拦截 ，如果说在preview里有没有log拦截失败，不要猜    2.  如果preview你拦截不了，后需要想办法，包括在某些特定的群聊上关掉preview，跟微信一样显示最终解果后能拦截也行"

## 两条方法论

### 1. **不猜——加 log 看实际拦截状态**

- "preview 里的拦截有没有触发" = 靠 log 确认，**不靠脑补"我以为它会触发"**
- 改任何拦截逻辑前先在拦截点加 log
- 跑一次场景看 log 里有没有"拦截"标记
- 没看到标记 = 拦截没生效 = 改设计
- **看到标记但还是出问题** = 拦截逻辑错，改逻辑

### 2. **拦不了的兜底：特定场景关掉中间状态**

- preview 拦不了 = **在该场景下关掉 preview**（像微信一样直接显示最终结果）
- 配置化：`channels.group.previewEnabled` 默认 true，false 时 degraded
- **不要在所有地方都强求"完美拦截"**——能拦就拦，拦不了就让用户走"延迟显示+最终拦截"路径

## Why

1. **我之前在 preview 流式 chunk 级拦截的判断**：看到 "preview 通过 editPreview 推到 Discord" 就说"这个无法事后拦截，prompt层控制"
   - **这就是猜**——我没看 log 确认 appendText 累积时实际状态
   - 翀哥说"不要猜" = 让我先加 log 跑一次看实际

2. **兜底方案思维**：遇到拦不了的情况，**降级体验换取功能**（关 preview 显示慢一点但能拦），而不是放弃

3. **跟之前"先找根因再改_0616"是同一思路的延伸**：那一条是"先验证再动手"，这一条是"先验证再下结论"

## How to apply

1. **改任何拦截逻辑前**：在拦截点加 log（标记"已拦截/未拦截"原因）
2. **跑一次场景看 log**：没看到标记 = 设计错了；看到标记 = 逻辑错了
3. **拦不了的兜底**：
   - 流式 chunk 级拦不了 → 关掉流式显示，直接显示最终结果
   - 实时检测不现实 → 用延迟检测（onResult）+ 兜底策略
4. **配置化兜底**：`channels.{group,dm,channel}.previewEnabled` 这类开关，让翀哥按群配置
5. **猜出来的结论不加 log 验证 = 浪费翀哥时间远程 debug**

## 跟 6/16 教训"先找根因再改"的关系

- 6/16 "先找根因再改"：排查问题不能猜，必须拿直接证据
- 6/18 "先打日志验证再下结论"：实施拦截/修法时不能猜，必须加 log 看实际

**升级版**：从"找根因不能猜" → "找完根因改的时候也不能猜，每一步都加 log 验证"
