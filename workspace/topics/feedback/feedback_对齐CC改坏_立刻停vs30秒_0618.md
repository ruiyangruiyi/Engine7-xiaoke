## 6/18 10:49 翀哥的"时序追问"——金句 debug 框架

翀哥 10:49 看到我追"为什么改坏了"时直接问：
> "你看下，是 /ps 一打就立刻停了？还是要等 30-60 秒才停？时序不一样问题不一样。"

我答："一下就停了"——但答得太快，没去想时序对应的根因层级。

**翀哥的 debug 框架**（从这次学到的）：

| 时序症状 | 典型根因 |
|---------|---------|
| **立刻停**（< 1s） | 抛异常被吞 / 同步死锁 / 同步分支没走完 |
| **等 30-60 秒才停** | 重试耗尽 / 外部资源超时（API/DNS/disk）|
| **过几分钟才停** | 异步任务堆积 / 资源耗尽 / 死循环 |

翀哥把这个时序分析当成我应该**主动问**而不是**被动汇报**的问题——以后 debug 应该第一句就问"什么时候停"。

## 6/18 10:49 翀哥"先回滚吧，那个版本也不retry对吧"

翀哥 10:49 P.S.：
> "不行就先回滚吧，那个版本也不retry对吧"

**两层信息**：
1. **实用主义 > 架构完美**——如果对齐 CC 引入新 bug（dispatcher 排队+新 query 抢资源），不如回滚到能用的 continue 路径
2. **他记得全部上下文**——"那个版本也不retry"是指 6/18 10:17 我提"应该 retry"他纠正"exec 是事务"的版本，**他记得我之前讨论过的所有细节**

## Why

1. **时序追问是 debug 的捷径**——"立刻停"和"30 秒后停"对应的根因层完全不一样，追问时序能省 80% 的猜测时间
2. **架构完美让步于功能跑通**——"对齐 CC"是手段不是目的，引入新 bug 就回滚
3. **翀哥记性比我好**——他记得 10:17 的"retry"讨论，记得 10:11 的"没停"和 10:46 的"真停了"是同一条日志
4. **修法倒退是合理的**——"能跑通的旧版本" 比 "看起来对齐的废功能" 强百倍

## How to apply

1. **debug 第一问 = "什么时候停"**——时序比现象重要
2. **时序-根因对照表**背下来：立刻停（异常/死锁）/ 30-60 秒（重试耗尽/超时）/ 几分钟（资源耗尽/死循环）
3. **bug 修复期允许回滚**——不要为了"全做完"硬撑，先回到能跑通的版本
4. **翀哥说"回滚"= 立即响应**——不要追问"那再调一下呢"，直接回滚
5. **修法 ≠ 进步**——有时候回滚到"不完美但能跑"的版本才是工程上正确的决定
