## 整体链路

```
浏览器点击 carpo 按钮
  ↓ HTTP POST /carpo-trigger
server.py (8088)
  ↓ SSH exec → 235 HTTP POST /generate
235 carpo_avatar_server.py
  ├─ dashscope TTS streaming
  ├─ FlashHead 推理 (并行)
  └─ SDK push → 北京 23800
北京 Carpo server (192.144.156.158:23800)
  ↓ RTP relay
server.py SDK pull (Carpo.dll callbacks)
  ├─ PyAV Opus decode (audio)
  ├─ PyAV H264 decode (video)
  └─ WebRTC emit → 浏览器
浏览器 audio.playing / video.playing
```

## 一、235 端 timing 字段

| 字段 | 时钟 | 来源 | 含义 |
|------|------|------|------|
| `t_request_received` | `time.time()` | generate() 第一行 | HTTP 请求到达 235 的时刻 |
| `t_tts_first_chunk` | `time.time()` | for 循环第一次迭代 | dashscope TTS 第一个 PCM chunk 到达 |
| `t_tts_last_chunk` | `time.time()` | for 循环结束后 | dashscope TTS 最后一个 chunk 到达 |
| `t_push_audio_first` | `time.time()` | _push_worker 第一次 push audio | SDK 第一次 push audio RTP packet |
| `t_push_video_first` | `time.time()` | _push_worker 第一次 push video | SDK 第一次 push video RTP packet |
| `t_push_audio_last` | `time.time()` | _push_worker 每次 push audio | SDK **最近一次** push audio RTP packet |
| `t_push_video_last` | `time.time()` | _push_worker 每次 push video | SDK **最近一次** push video RTP packet |
| `t_request_returned` | `time.time()` | generate() return 前 | HTTP 200 返回给调用者 |
| `total` | 同上 | elapsed = t_request_returned - t_request_received | generate() 总耗时 |

**关键**: `t_push_audio_last` 是实时更新的，不是"最后一次 TTS"。Idle 期不会更新这个值。如果拿它跟 server pull 时刻对比，idle gap 会被当成网络延迟。

**TTS 延迟分解**:
- `t_tts_first_chunk - t_request_received` ≈ 0.5-1s (dashscope API 首字延迟)
- `t_tts_last_chunk - t_request_received` ≈ 1-2s (dashscope 全部 TTS 时长)
- FlashHead 不在这个路径上 (独立后台线程并行推理)

## 二、server.py 端 timing 字段

### 时钟转换

```python
_SERVER_BOOT_MONOTONIC = time.monotonic()  # server 启动时记
_SERVER_BOOT_UNIX = time.time()

def _mono_to_unix(mono_ts):
    return _SERVER_BOOT_UNIX + (mono_ts - _SERVER_BOOT_MONOTONIC)
```

server 内部全部用 monotonic，输出到 SSE 时才转 unix epoch。

### 字段详解

| 字段 | 时钟 | 来源 | 含义 |
|------|------|------|------|
| `cross_audio_latency_ms` | monotonic→unix | 每个 RTP packet 的 push timestamp | **同一个 packet** 的 235 push → server pull 时间差 |
| `cross_video_latency_ms` | monotonic→unix | 同上, video | 同上, video |
| `decode_to_emit_audio_ms` | monotonic | 每个 audio chunk decode→emit 差 | handler queue 延迟 (单帧) |
| `audio_queue_size_before` | - | `qsize()` 在 emit 前 | emit 前 queue 里积压几帧 |
| `t_pull_audio_first` | monotonic | 第一个 pull audio packet | server 收到第一个 audio packet |
| `t_emit_audio_first` | monotonic | 第一次 emit | WebRTC 首次推音频 |
| `unix_pull_audio_first` | monotonic→unix | first pull 转换 | 跟 235 t_push_* 同 epoch |
| `audio_count` / `video_count` | - | 每个 packet +1 | server 启动以来收到的包数 |

### cross_audio_latency_ms 的计算

```python
timestamp = callback_arg  # SDK pull 回调给的 timestamp (ms, 来自 235 push 时)
server_pull_unix = _SERVER_BOOT_UNIX + (_now - _SERVER_BOOT_MONOTONIC)
cross_latency_ms = (server_pull_unix - timestamp / 1000.0) * 1000
# sanity check: 0 < latency < 5000ms (公网 RTP 正常 50-200ms)
if 0 < cross_latency_ms < 5000:
    _last_cross_audio_latency_ms = cross_latency_ms
```

⚠️ **这是最准确的实时跨机器延迟**。每个 packet 单独算，不依赖 idle gap。
⚠️ 依赖 SDK push timestamp 的精度（SDK 内部的 RTP timestamp 可能跟 unix 有 offset）。

### decode_to_emit_audio_ms 的计算

```python
# SDK pull callback:
audio_queue.put((chunk, decode_ts))  # 把 decode_ts 一起塞入 queue

# handler emit:
audio, decode_ts = queue_item
emit_ts = time.monotonic()
raw_ms = (emit_ts - decode_ts) * 1000
```

- 0-50ms: handler queue 空的, emit 立刻消费 → **正常**
- 几百ms: queue 积压 → **需要优化**
- 负数: queue 很大, 取出的 chunk 是几秒前的 → **不精确**

⚠️ 这个值是**最新一帧**，不是平均。每 0.5s snapshot 取最近一帧。

### unix_pull_audio_first vs unix_pull_audio_last 的区别

- `first`: server 启动后第一次收到 audio packet (含 init 延迟)
- `last`: 最近一次收到 audio packet (实时)
- ❌ **不要拿 `last` 跟 235 `t_push_audio_last` 做差** — 两个不同 packet，idle gap 会被当成延迟

## 三、浏览器端 timing 字段

| 字段 | 时钟 | 来源 | 含义 |
|------|------|------|------|
| `t_play_audio_browser` | `Date.now()/1000` | audio.playing 事件 | 浏览器听到声音的时刻 (unix 秒) |
| `t_play_video_browser` | `Date.now()/1000` | video.playing 事件 | 浏览器看到画面的时刻 |
| `t_send_command_browser` | `performance.now()` | 点击 carpo 按钮时 | 用户触发时刻 |

### 235 req → 浏览器 play (端到端)

```js
e2e = t_play_audio_browser - t235.t_request_received
// 只算一次 (playing 事件触发时), 不每次 SSE 都重算
// sanity check: 0.3 < e2e < 10s
```

- 正常: 1-5s (dashscope ~1.5s + 网络 ~0.2s + 浏览器 buffer ~0.3s)
- 负数: playing 在 request 之前 (来自上一轮 TTS) → discarded
- >10s: 异常 → discarded

## 四、刷新频率

| 数据源 | 频率 | 推送方式 |
|--------|------|----------|
| 235 timing dict | 每次 /generate 1 次 | SSE timing_235 event |
| server latency snapshot | 每 0.5s | SSE latency event |
| 跨机器实时延迟 | 每个 RTP packet | 每次 snapshot 取最新 |
| 浏览器 play 时刻 | playing 事件触发时 | 单次 |

## 五、正确 vs 错误的使用方式

| ❌ 错误 | ✅ 正确 |
|--------|--------|
| `unix_pull_audio_last - t_push_audio_last` (idle gap 被当成延迟) | `cross_audio_latency_ms` (同 packet) |
| 每次 SSE 事件都算 e2e (数字越来越大) | playing 事件算一次, sanity check |
| `t_emit_audio_first - t_decode_audio_first` (init 延迟) | `decode_to_emit_audio_ms` (单帧实时) |
| performance.now() 跟 time.time() 混用 | 都用 Date.now()/1000 或都用 time.time() |
