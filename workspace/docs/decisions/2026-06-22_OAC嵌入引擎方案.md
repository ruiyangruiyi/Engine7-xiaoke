# OAC 嵌入引擎方案

> 日期：2026-06-22 | 作者：小柯 | 基于：OAC 源码精读 + engine channel 架构分析

## 核心结论

**OAC 已经写好了和外部引擎通信的桥（OC Bridge）。我们引擎只需要加一个 HTTP webhook endpoint。不需要改 OAC 源码，不需要写新 channel adapter。**

## 架构图

```
浏览器 ←WebRTC→ OAC 后端（Python, 独立进程）
                    │
                    ├── VAD（Silero）
                    ├── ASR（SenseVoice/paraformer）
                    ├── Perception（qwen3-vl-flash 视觉理解）
                    ├── TTS（CosyVoice/GPT-SoVITS）
                    ├── Avatar（MuseTalk 嘴型同步）
                    │
                    └── OC Bridge
                         │
                         │ POST /webhook/oac-bridge
                         │ {oac_session_id, text, sender_name}
                         ▼
              Engine（TS, 独立进程）
                    │
                    ├── 收到 text → MessageDispatcher → QueryEngine
                    ├── LLM 回复 → stream text
                    │
                    │ POST /oc-reply → OAC callback :8011
                    │ {oac_session_id, text}
                    ▼
              OAC 收到回复 → TTS → Avatar → 推流
```

## 数据流详解

### 1. 用户说话 → 引擎回复

```
1. 用户对 mic 说话
2. OAC: VAD 检测语音活动 → ASR 转文字 (HUMAN_TEXT)
3. OAC: ChatAgent 或 SimpleLLM handler 收到 HUMAN_TEXT
4. OAC: 如果用 ChatAgent + OC Bridge:
   - POST /webhook/oac-bridge → Engine
   - body: {oac_session_id, text, sender_name}
5. Engine: webhook handler 收到 text
   - 转成 InboundMessage {channel: 'oac', from: oac_session_id}
   - → ChannelManager → MessageDispatcher → QueryEngine
6. Engine: LLM 回复 → stream text chunks
   - 积累完整回复 (或分段)
   - POST /oc-reply → OAC callback :8011
   - body: {oac_session_id, text}
7. OAC: 收到回复 → TTS → Avatar → WebRTC 推流
```

### 2. 视觉链路（并行）

```
1. 摄像头 30fps → PerceptionHandler
2. 每 3-5s 抽帧 → qwen3-vl-flash 生成描述
3. 描述注入 ChatAgent 的 prompt（L3 environment_state）
4. 不阻塞对话主链路
```

## 需要改 Engine 什么

### 最小改动：加一个 HTTP webhook handler

在 engine-startup.ts 里加一段：

```typescript
// OAC Bridge webhook — 收 OAC 发来的消息
const http = require('http')
const oacServer = http.createServer((req, res) => {
  if (req.method === 'POST' && req.url === '/webhook/oac-bridge') {
    let body = ''
    req.on('data', chunk => body += chunk)
    req.on('end', () => {
      const { oac_session_id, text, sender_name } = JSON.parse(body)
      // 转成 InboundMessage 投递
      const msg: InboundMessage = {
        content: text,
        from: oac_session_id,
        fromName: sender_name,
        channel_id: oac_session_id,
        channel: 'oac',
        channelType: 'dm',
      }
      // 通过 dispatcher 投递（复用现有消息流程）
      channelManager.handleInbound(msg)
      res.writeHead(200, { 'Content-Type': 'application/json' })
      res.end(JSON.stringify({ ok: true }))
    })
  }
})
oacServer.listen(18789, () => console.log('[oac-bridge] listening on :18789'))
```

**但 handleInbound 是 private**——需要改成 public，或者直接调 messageHandler。

### 回复路径

Engine 的 stream handler 需要判断：如果消息来自 OAC channel，回复不走 Discord/飞书 API，而是 POST 到 OAC callback :8011/oc-reply。

这部分需要在 engine-startup.ts 的 stream 回复逻辑里加分支：

```typescript
if (msg.channel === 'oac') {
  // POST 回 OAC callback
  await fetch('http://localhost:8011/oc-reply', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ oac_session_id: msg.from, text: replyText })
  })
} else {
  // 正常 Discord/飞书/微信回复
  channelManager.send(msg.channel, msg.channel_id, replyText)
}
```

## 需要改 OAC 什么

### 理想情况：不改

OAC 的 OC Bridge 已经写好了：
- `oc_channel_client.py:222-247` — send_message 发 webhook
- `oc_channel_client.py:84-143` — callback server 收回复
- 配置默认连 `localhost:18789`

**只要 Engine 在 :18789 起 webhook server，OAC 就能直接连上。**

### 可能需要调的

1. **OAC 配置**：`config/chat_with_..._agent.yaml` 里配 OC Bridge 的 gateway_url 和 callback_port
2. **OAC 用 ChatAgent 而不是 SimpleLLM**：需要配 `chat_agent_handler` + `oc_bridge` handler

## 两种集成模式对比

### 模式 A：OC Bridge（推荐——最小改动）
- OAC 用 ChatAgent handler + OC Bridge
- Engine 加 webhook endpoint
- **OAC 和 Engine 是两个独立进程，HTTP 通信**
- 优点：不动 OAC 源码，不动 engine channel 架构
- 缺点：HTTP 往返有延迟（本地 ~5ms）

### 模式 B：替换 OAC 的 LLM Handler
- 写一个 `llm_handler_engine.py`，OAC 内部调 engine HTTP API
- 不走 OC Bridge 的 webhook 双向通信
- 优点：OAC 内部 LLM handler 可以流式拿 token
- 缺点：要写新 handler，且 OC Bridge 的记忆/工具/persona 都用不上

**推荐模式 A**——翀哥的 engine 已经有完整的记忆+工具+persona，OC Bridge 只是让 OAC 把对话转发给 engine。

## 延迟分析

| 环节 | 延迟 | 备注 |
|------|------|------|
| VAD 端点检测 | ~2s | **最大瓶颈**——OAC 内部 |
| ASR 推理 | 65-200ms | SenseVoice 非流式 |
| OC Bridge HTTP 往返 | ~5ms | 本地 localhost |
| Engine LLM 首 token | 300-800ms | GLM-5.2/M3 |
| OC Bridge 回复 HTTP | ~5ms | 本地 |
| TTS 首句 | 200-500ms | CosyVoice/GPT-SoVITS |
| Avatar 嘴型 | 30-50ms/帧 | MuseTalk GPU |
| **全链路首字** | **~3-4s** | VAD 占 2s |

**优化方向**：
1. VAD end_delay 从 2s 降到 0.5s（改 OAC 配置）
2. ASR 换 paraformer-zh-streaming（流式，省 VAD 确认延迟）
3. TTS 集成 SentenceAwareTokenBuffer（分句流式合成）

## 落地步骤

### Step 1: Engine 加 webhook endpoint（1-2 小时）
- engine-startup.ts 加 HTTP server 监听 :18789
- 收到 /webhook/oac-bridge → 转成 InboundMessage → dispatcher
- LLM 回复 → POST 回 OAC callback :8011/oc-reply
- 验证：curl 测 webhook，看 engine 是否收到

### Step 2: OAC 配 OC Bridge（30 分钟）
- 复制 `config/chat_with_..._agent.yaml`
- 配 oc_bridge handler：gateway_url=localhost:18789, callback_port=8011
- 验证：OAC 启动看是否连上 engine

### Step 3: 端到端测试（1 小时）
- 浏览器开 OAC → 说话 → ASR → engine → TTS → Avatar
- 测视觉：摄像头 → Perception → 注入 prompt
- 测打断：说话中途 stop

### Step 4: 优化延迟（后续）
- VAD end_delay 调小
- ASR 换流式
- TTS 分句流式

## 风险

1. **OAC 的 ChatAgent 和 OC Bridge 是否真能用**——源码有但可能没测过
2. **Engine :18789 端口是否被占**——需要确认
3. **OAC 回复路径延迟**——如果 engine LLM 流式输出，OAC 要等完整回复才能 TTS。后续可以改成 SSE 流式推送 token 给 OAC

## 不确定的点（等翀哥拍板）

1. **OAC 后端是本地跑还是 Docker？** Docker 有 GPU 直通问题
2. **ASR 用 SenseVoice 还是 paraformer-zh-streaming？** 翀哥之前说 paraformer 65ms，但 OAC 默认是 SenseVoice 非流式
3. **TTS 用 CosyVoice 还是 GPT-SoVITS？** 翀哥说 GPT-SoVITS（张小媒声音），但 OAC 默认是 CosyVoice
4. **Engine 的 webhook 跑在 engine 进程里还是独立进程？** 跑 engine 里最简单，但端口管理要小心
