## 一、FlashHead 处理器架构

### 核心参数

```python
frame_num = 33              # 推理总帧数
motion_frames_num = 9       # overlap 帧（丢弃）
slice_len = 24              # 33 - 9 = 24（实际输出帧数）
tgt_fps = 25                # 目标帧率
sample_rate = 16000         # 算法输入采样率
output_audio_sample_rate = 24000  # 输出音频采样率
cached_audio_duration = 8   # 滑动窗口秒数

audio_slice_samples = slice_len * sample_rate // tgt_fps
    = 24 * 16000 // 25 = 15360 samples @ 16kHz ≈ 1秒

_original_audio_per_frame = output_sr // tgt_fps
    = 24000 // 25 = 960 samples @ 24kHz = 40ms

_original_audio_slice_samples = slice_len * output_sr // tgt_fps
    = 24 * 24000 // 25 = 23040 samples @ 24kHz ≈ 0.96秒
```

### 数据流

```
TTS PCM (流式小块) → add_audio()
  → _pending_audio 累积
  → 攒满 15360 samples (1秒) → _process_chunk() 推理一次
    → GPU 推理生成 33 帧（丢前 9 帧 overlap）
    → 输出 24 帧 video + 配对 23040 samples audio
    → 24 个 FrameQueueItem 入 _output_queue
      每个 item: video_frame(BGR 512×512) + audio_segment(960 samples)

frame_collector_worker (25fps 节拍器)
  → 每 40ms 从队列取 1 个 item
  → 调 callback: on_video_frame + on_audio_frame

idle_inference_worker (后台线程)
  → 队列 < 12 帧且没说话时
  → 用呼吸噪声生成 idle 动画帧填充队列
  → 每 100ms 检查一次
```

### 三条线程

| 线程 | 职责 | 节奏 |
|------|------|------|
| `_process_chunk` | TTS 驱动的推理 | 有 audio 就跑（4090 上 ~0.25s/次） |
| `_idle_inference_worker` | idle 帧（呼吸噪声） | 队列空时填充，100ms 轮询 |
| `_frame_collector_worker` | 25fps 输出 | 严格 40ms tick |

### frame_collector 的节奏控制（关键）

```python
# line 434-442 — 绝对时间节拍，不管队列积压多少
target_time = start_time + frame_id * frame_interval  # frame_id × 0.04s
sleep_time = target_time - now
if sleep_time > 0.002:
    time.sleep(sleep_time - 0.001)
while time.perf_counter() < target_time:
    pass  # spin wait
# 每 40ms 取一帧，不会全速 drain
```

**frame_collector 是 25fps 节拍器。即使队列积压几百帧，也每 40ms 只取 1 帧。**

### audio_segment=None 的原因

```python
# _process_chunk line 296-309
for i in range(n_frames):  # 24 帧
    frame_bgr = frames_np[i]
    audio_start = i * 960   # 每帧配 960 samples
    if audio_start < len(original_audio):
        audio_seg = original_audio[audio_start:audio_end]
    else:
        audio_seg = None    # audio 不够配了！
```

一次推理输出 24 帧，需要 24 × 960 = 23040 samples。如果 `original_audio` 不足 23040，后面的帧 audio_seg=None。

**OAC 不受影响：fastrtc 的 audio track 独立运行，不依赖每帧都有 audio。**
**我们受影响：push_audio 必须每帧调才能保持 RTP 流连续。**

## 二、OAC vs 我们的链路对比

| 维度 | OAC | 我们 |
|------|-----|------|
| FlashHead 输出 | BGR + PCM (raw) | BGR + PCM (raw) — 相同 |
| 编码 | fastrtc (aiortc) 在推送时编码 | carpo_oac_bridge 编码后推 |
| 传输 | WebRTC P2P | Carpo RTP push → server → pull |
| 解码 | 浏览器解码 | SDK pull 端解码 |
| 再编码 | 无 | fastrtc 再编码给浏览器（未来可优化：直接传编码数据） |
| AV 同步 | fastrtc 各 track 独立 PTS + RTCP SR | Carpo SDK baseMediaTs + getOutPutTimeStamp |

**我们比 OAC 多一轮编解码：push 编码 → RTP → pull 解码 → fastrtc 再编码 → 浏览器解码**

优化方向：pull 端不解码，直接把 H.264 NAL + Opus 给 fastrtc。

## 三、Carpo SDK timestamp 机制

### push 端

```
sendMediaData(type, buf, size, timestamp_ms)
  → getPacketTimestamp(type, timestamp_ms):
      baseMediaTs = min(audio 首帧 ts, video 首帧 ts)
      assert(timestamp >= baseMediaTs)
      return timestamp_ms - baseMediaTs  ← 相对毫秒
  → RTPPacker::calcPtsHZ(type, relative_ms):
      video: relative_ms × 90   (90kHz)
      audio: relative_ms × 48   (48kHz, 用 AAC_AUDIO_SAMPLE_RATE=48000)
  → RTP timestamp = calcPtsHZ 返回值
```

**push 端传入的 timestamp 必须是毫秒。** audio 和 video 共享 baseMediaTs。

### pull 端

```
VideoRTPReceiver: param.pts = RTP_ts / 90  ← 还原 ms
AudioRTPReceiver: NetEq 内部处理，输出 playout timestamp
  → pts = playout_ts / 48  ← 还原 ms（但 NetEq 可能变速）

getOutPutTimeStamp(type, nal_type, pkt_ts_ms, out_ts):
  IF pkt_ts < time_stamp_rebase:
    time_stamp_rebase = -1   ← 重置
    return -1                ← 帧丢弃
  IF time_stamp_rebase == -1:
    IF video 且 nal_type == 7 (SPS):
      time_stamp_rebase = pkt_ts  ← 设基准
    ELSE:
      return -1              ← 等 SPS
  out_ts = pkt_ts - time_stamp_rebase
```

**pull 端 audio/video 共享同一个 time_stamp_rebase。** video SPS 设基准，之后所有帧（audio+video）跟它比。

### 关键：NetEq 变速

AudioRTPReceiver 用 WebRTC NetEq 做 jitter buffer。NetEq 会根据网络状况**加速或减速**音频播放，输出的 playout timestamp 跟输入 RTP timestamp 不完全一致。

**video 的 JitterBuffer 不改 timestamp。** 所以长时间运行后 audio 和 video 的 ms 值会偏移。

## 四、当前问题与已尝试方案

### 问题 1（已解决）：NAL 拆分 + SPS/PPS/IDR

**解决：** 3+4 byte start code 拆分 + SEI skip + threads=1/closed-gop。

### 问题 2（已解决）：video timestamp syncing SPS 死循环

**根因：** push 端 audio/video 的 timestamp 不对齐。
**解决：** 改成独立 PTS 计数器，各自从 0 起步。

### 问题 3（进行中）：AV pts 不同步

**现象：**
```
vpts = 6886600ms（172165 帧 × 40）
apts = 1455800ms（36395 次 × 40）
video 是 audio 的近 5 倍
```

**根因分析：**

1. **on_video_frame 被调了 172165 次，on_audio_frame 只 3 次**
   - speaking 帧的 audio_segment=None → 不调 on_audio_frame
   - frame_collector 的 speaking 分支有条件调 audio

2. **frame_collector 不是 25fps？frame=172165 几分钟跑完**
   - frame_collector 应该严格 25fps（绝对时间节拍）
   - 但实际帧数远超 25fps × 时间
   - **需要确认 frame_collector 在 268 上是否正确限速**

3. **on_video_frame 里同时推 audio 的方案导致 audio pts 暴涨**
   - 每帧都 push_audio(静音) → _audio_pts += 40
   - 如果 frame_collector 全速跑 → audio pts 暴涨

### 待验证

- **frame_collector 是否真的 25fps？** 需要在 callback 入口加 `time.time()` 打 wall timestamp
- **如果 frame_collector 确实 25fps，pts 应该正确**（vpts = frame × 40ms）
- **如果 pts 正确，audio pts 应该跟 video pts 对齐**（on_video_frame 里同时推 audio）
