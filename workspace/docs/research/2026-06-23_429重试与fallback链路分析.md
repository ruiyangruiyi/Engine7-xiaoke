# 429 重试与 fallback 链路分析

> 日期：2026-06-23 | 作者：小柯 | 目的：搞清楚 429 quota 错误经过哪些层，为什么没被正确拦住

## 三层架构总览

```
query.ts (QueryEngine)          ← 第3层：agent loop，收到 error 后自己 retry 3 次
  ↓ this.provider.streamChat()
fallback-provider.ts            ← 第2层：多模型 fallback + 24h cooldown
  ↓ entry.provider.streamChat()
anthropic-provider.ts           ← 第1层：调 API，内部用 fetchWithRetry
  ↓ fetchWithRetry()
withRetry.ts                    ← 第0层：HTTP fetch + shouldRetry 判断
```

## 第0层：withRetry.ts — HTTP 重试

**文件：** `src/services/withRetry.ts`

### shouldRetry() (L86-129)

```typescript
function shouldRetry(status: number, errorBody?: string): boolean {
  if (status === 529) return true          // Overloaded → 重试

  if (status === 429) {
    const body = errorBody?.toLowerCase() || ''
    if (
      body.includes('insufficient_quota') ||
      body.includes('allocationquota') ||        // ← 子串匹配，能匹配到 "throttling.allocationquota"
      body.includes('quota_exceeded') ||
      body.includes('quotaexceeded') ||
      (body.includes('quota') && body.includes('exceeded'))
    ) {
      return false    // ← 配额用完，不重试
    }
    return true       // ← 普通 429 rate limit，重试
  }

  if (status === 408) return true   // timeout
  if (status === 409) return true   // conflict
  if (status === 401) return true   // auth
  if (status === 403) return true   // forbidden
  if (status >= 500) return true    // server error
  return false                      // 其他不重试
}
```

### fetchWithRetry() (L149-263)

```
for (attempt = 1; attempt <= 11; attempt++) {
  response = await fetch(url)

  if (!response.ok) {
    // 只在 429/529/500+/400 时读 body
    errorBody = await response.clone().text()

    if (shouldRetry(status, errorBody)) {
      yield { type: 'api_retry', ... }   // ← yield 重试消息
      await sleep(delay)
      continue                            // ← 重试
    }

    // shouldRetry 返回 false → 直接返回原始 response（不重试）
    return response
  }

  return response  // 成功
}
```

**结论：withRetry 层对 `AllocationQuota` 的判断是正确的。**
- `errorBody` = `{"code":"Throttling.AllocationQuota","message":"..."}`
- 转小写后 `.includes('allocationquota')` → true → `shouldRetry` 返回 false → 不重试 → 返回 429 response

## 第1层：anthropic-provider.ts — Provider

**文件：** `src/models/anthropic-provider.ts`


**结论：anthropic-provider 收到 429 response → yield error chunk。**
- error 内容 = `"Anthropic API 429: {"code":"Throttling.AllocationQuota",...}"`
- 这个 error chunk 发给调用者（FallbackProvider 或 QueryEngine）

## 第2层：fallback-provider.ts — 多模型 fallback

**文件：** `src/models/fallback-provider.ts`

### streamChat() (L64-141)

```
1. 找第一个不在 cooldown 的候选 → activeEntry
2. 如果全在 cooldown → 用第一个（强制探测）
3. 调 activeEntry.provider.streamChat()
4. 收到 error chunk (L97):
   - setCooldown(activeEntry)     ← 进 24h 冷静期
   - 找下一个不在 cooldown 的 → nextEntry
   - 找到 → yield status → 递归调 this.streamChat() → 切到 nextEntry
   - 找不到 → yield error chunk（透传给上层）← 关键！
```

**当三个 fallback 都在同一 Token Plan 时：**
```
model A (dashscope-tp) → 429 → cooldown → 切 B
model B (zai-anthropic) → 429 → cooldown → 切 C
model C (deepseek) → 429 → cooldown → 没有候选了 → yield error（透传）
```

**结论：FallbackProvider 在所有候选都挂了时，yield error chunk 给 QueryEngine。**

## 第3层：query.ts — QueryEngine agent loop

**文件：** `src/core/query.ts`

### streamChat() 里收到 error chunk (L306-330)

```typescript
for await (const chunk of this.provider.streamChat({ ... })) {
  // ...
  if (chunk.type === 'error') {
    const errMsg = chunk.error || 'unknown stream error'
    console.log(`Turn ${turnCount}: API stream error: ${errMsg}. Retrying...`)
    streamError = errMsg
    break    // ← break 出 for-await
  }
}

// ↓ break 后到这

// Stream error retry
if (streamError) {
  const MAX_STREAM_RETRIES = 3
  const delay = Math.min(1000 * Math.pow(2, streamRetries), 16_000)
  if (streamRetries < MAX_STREAM_RETRIES && !ac.signal.aborted) {
    // ← 无条件 retry！不看错误内容！
    streamRetries++
    continue    // ← retry 整个 turn
  }
  // 3 次 retry 后
  yield { type: 'error', error: streamError }
  return
}
```

**⚠️ 这是问题核心：**

query.ts 收到 FallbackProvider 透传上来的 error chunk 后，**不看错误内容，无条件 retry 3 次**。

每次 retry 又重新调 `this.provider.streamChat()`，也就是又走一遍 FallbackProvider：
- 所有候选都在 cooldown → force probe model A → 429 → setCooldown → 全挂 → yield error
- query.ts 收到 error → retry 第 2 次 → 又走一遍 → 全挂 → yield error
- retry 第 3 次 → 又走一遍 → 全挂 → yield error
- 3 次 retry 用完 → yield error → 最终返回给用户

**实际日志（2026-06-22 12:56）：**
```
Turn 1: API stream error: ...AllocationQuota... Retrying...
Turn 2: API stream error: ...AllocationQuota... Retrying...
Turn 3: API stream error: ...AllocationQuota... Retrying...
Turn 4: stream error after 3 retries: ...AllocationQuota...
```

## 完整链路（429 AllocationQuota 场景）

```
1. query.ts: this.provider.streamChat()
2.   → FallbackProvider.streamChat()
3.     → model A (dashscope-tp) → anthropic-provider.streamChat()
4.       → fetchWithRetry() → fetch() → HTTP 429
5.       → shouldRetry(429, body) → body.includes('allocationquota') → false → 不重试
6.       → 返回 429 response 给 anthropic-provider
7.     → anthropic-provider: !response.ok → yield error chunk
8.     → FallbackProvider 收到 error → setCooldown(A) → 切 model B
9.     → model B (zai-anthropic) → 同上 → 429 → error
10.    → FallbackProvider: setCooldown(B) → 切 model C
11.    → model C (deepseek) → 同上 → 429 → error
12.    → FallbackProvider: setCooldown(C) → 没有候选 → yield error（透传）
13. → query.ts 收到 error chunk → streamError = errMsg → break
14. → query.ts L317: 无条件 retry 3 次 → 每次重复步骤 2-12
15. → 3 次 retry 用完 → yield error → 返回给用户
```

## 问题总结

| 层级 | 429 quota 处理 | 状态 |
|------|---------------|------|
| withRetry.ts | ✅ shouldRetry 正确判断，不重试 | 正常 |
| anthropic-provider.ts | ✅ 收到 429 response → yield error | 正常 |
| fallback-provider.ts | ⚠️ 能切候选，但所有候选共享 Token Plan → 全挂 → 透传 error | 正常（但场景限制） |
| **query.ts** | **❌ 无条件 retry 3 次，不看错误内容** | **问题在这** |

## 根因

**query.ts L317-330 对所有 stream error 统一 retry 3 次，不区分错误类型。**

- `AllocationQuota` / `insufficient_quota` 这种"额度耗尽"的错误，retry 没有任何意义
- 每次 retry 又走一遍 FallbackProvider 的全链路（3 个 model 各打一遍），浪费时间 ~30s
- 最终结果跟不 retry 完全一样——全挂

## 历史背景

6/22 09:24-09:26 加了 `shouldRetry` 对 quota 类错误的判断（commit 86f57dc + f3718a5），**但只改了 withRetry.ts（第0层）**，query.ts（第3层）的无条件 retry 没改。

当时以为 withRetry 层拦住就够了，没注意到 query.ts 还有自己的一层 retry。
