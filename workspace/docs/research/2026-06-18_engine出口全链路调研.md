# Engine 消息出口全链路调研

**日期**：2026-06-18
**目的**：摸清所有"消息出口"——即 engine 把 AI 生成内容发到外部（Discord/飞书/微信）的代码路径。这是做敏感词拦截的前置工作。
**结论先放**：出口有 5 个底层方法 + 2 大类（passive 被动响应 / active 主动调用），共 17+ 个调用点。

---

## 一、底层出口（5 个方法）

`channelManager` 提供 18 个公开方法，其中**发消息的只有 5 个**：

| 方法 | 用途 | 文件 |
|---|---|---|
| `send(channelName, target, message, options?)` | 发文本消息 | `src/channels/manager.ts` |
| `sendFile(channelName, target, message, attachment)` | 发媒体（图片/文件/音频） | `src/channels/manager.ts` |
| `sendPreview(channelName, channelId, content, agentName?)` | 发流式 preview 占位 | `src/channels/manager.ts` |
| `editPreview(channelName, handle, content, agentName?, isFinal?)` | 编辑 preview（打字机） | `src/channels/manager.ts` |
| `deletePreview(channelName, handle)` | 删除 preview | `src/channels/manager.ts` |

> **没有** `replyTo` / `broadcast` / `reply` / `dm` 等独立方法。reply 走 `send(..., { replyTo: messageId })` 的 options。

这 5 个方法内部委托给 adapter：

- **Discord** (`src/channels/discord.ts`)：原生 discord.js（`channel.send` / `origMsg.reply` / `messages.delete`）
- **飞书** (`src/channels/feishu.ts`)：`client.im.message.create` / `patch` / `delete`
- **微信** (`src/channels/wechat.ts`)：iLink API（无编辑/删除 API，preview 是伪 preview）

## 二、调用方分类

### A. Passive（被动响应）—— LLM 主回复链路

这是用户发消息后，AI 自动回复的全链路。**绝大多数出口在这里**。

| 回调 | 触发 | 行为 | 出口 | 敏感词 |
|---|---|---|---|---|
| `onText` (L1754) | LLM 流式输出每个 chunk | `preview.appendText(text)` | `cm.sendPreview` / `editPreview`（节流：10 字符/800ms） | ❌ |
| `onThinking` (L1757) | thinking 累积到阈值 | `cm.send` 格式化文本 | `cm.send` | ❌ |
| `onToolCall` (L1766) | LLM 调工具 | `cm.send` 格式化 tool 调用 | `cm.send` | ❌ |
| `onToolResult` (L1778) | 工具返回结果 | `cm.send` 格式化结果 | `cm.send` | ❌ |
| `onError` (L1789) | LLM 错误 | `cm.send` 错误信息 | `cm.send` | ❌ |
| `onResult` (L1795) | agent loop 结束 | `preview.finish` → 失败则 `cm.send(..., {replyTo})` | `cm.send` | ❌ |

**关键路径**：
```
用户消息 → engine.query()
  ├─ onText(增量) → StreamPreview → sendPreview/editPreview
  ├─ onToolCall/Result → cm.send (无敏感词)
  ├─ onError → cm.send (无敏感词)
  └─ onResult(最终) → preview.finish
       ├─ delivered=true → preview 已是最终消息
       └─ delivered=false → cm.send(channel, channelId, response, {replyTo})
```

### B. Active（主动调用）—— LLM 工具出口

LLM 主动通过工具发消息到任意目标（跨平台/跨频道）。

| 工具 | 文件:行号 | 出口 | 敏感词 |

### D. Preview 系列（流式累积）

`src/channels/stream-preview.ts` 封装 preview 生命周期：

| 方法 | 行号 | 行为 |
|---|---|---|
| `appendText` | L78-102 | 累积到 `fullText` |
| `flush` | L202-233 | 节流推送：`sendPreview`（首次）/ `editPreview`（后续） |
| `finish` | L109-143 | 把 preview 更新为最终内容；返回 `delivered` 标志 |
| `discard` | L156 | 删 preview + degrade |
| `freeze` | L174 | 冻结：去掉蓝框 header |

> Preview **从不直接调 `cm.send`**——最终回答的 `cm.send` 是在 `onResult` 里调的。

## 四、敏感词覆盖现状

| 出口 | 是否过敏感词 |
|---|---|
| `msg_send` 工具 | ✅ 群聊检查（`msg-send.ts:146-154`） |
| `msg_husband` 工具 | ❌ 硬编码飞书 DM，逃逸 |
| `media_send` 工具 | ❌ 媒体文件 |
| `my_selfie` / `my_voice` | ❌ |
| onResult → `preview.finish` | ❌ |
| onResult → `cm.send` | ❌ |
| onText → `cm.sendPreview` / `editPreview` | ❌ |
| onThinking / onToolCall / onToolResult | ❌ |
| onError | ❌ |
| cron 投递 | ❌ |
| Swarm / Inbox Poller | ❌ |
| Slash 命令反馈 | ❌ |
| Engine 内部反馈（thinking/tool/err） | ❌ |

**结论**：只有 `msg_send` 工具有敏感词检查。**LLM 的正常回复（onText/onResult 链路）完全不经过任何敏感词检查**——这是上一轮白做的根因。

## 五、关键洞察

1. **prepend @姐姐 这种加法没用**：根因不是 prepend，是 LLM 回复链路根本没接敏感词
2. **真正能拦的 3 个点**：
   - `preview.finish` 返回 `delivered=false` 后 `cm.send`（L1803）—— 必拦
   - `onResult` 整段逻辑结束前（统一拦截点）
   - adapter 底层 `send` / `sendFile`（兜底，但 preview 走不到）
3. **流式 chunk 级拦截不靠谱**：preview 是流式的，敏感词可能跨 chunk 匹配不到
4. **adapter 的 catch 块是地雷**：L154 `catch { /* fallback */ }` 静默吞错，必须加 log
