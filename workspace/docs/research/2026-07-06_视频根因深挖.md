# 视频通路根因分析（凌晨深挖）

**日期：** 2026-07-06 03:15

## 核心问题

A+V 同时 push：audio 收到 78 包，video 0 包。`[XK_RTP]` log（doProcessSocketData 入口）不打印。

## 关键发现

### 1. is_connected_ 的 AND 条件

`processRtcpAppPacket` (line 1127-1137):
```cpp
if (ssrc == local_audio_ssrc_) → audio_is_connected = true
else if (ssrc == local_video_ssrc_) → video_is_connected = true

if (audio_is_connected && video_is_connected) → is_connected_ = true
else → return;  // 不创建 receiver！
```

**pull 端 local SSRC：** audio=99999, video=11111

**server 回 ACK 的 ssrc 字段填什么？** 这是关键未知数。

### 2. askPlay 发什么

```cpp
rtcp_app->setSSRC(local_video_ssrc_);    // SSRC = 11111
rtcp_app->setSsrcWatch(remote_video_ssrc_); // ssrcWatch = 67890
```

### 3. kaskPlay ACK 处理（line 1164）

只有 `is_connected_ = true` 后才执行：
```cpp
case kaskPlay: {
    video_rtp_receiver_ = new VideoRTPReceiver();   // ← 只在这里创建！
    audio_rtp_receiver_ = new AudioRTPReceiver();
    timer_.addEvent(kTimerPopAudioPacket, ...);      // ← audio pop 定时器
}
```

如果 `is_connected_` 永远 false，receiver 永远不创建，`doProcessSocketData` 里 `video_rtp_receiver_` 为 null，video 包被丢弃。

### 4. 为什么旧 DLL 能收到 audio？

旧 DLL 测试时（pull_av4.log）确实收到了 78 包 audio。新 DLL 后（pull_av5.log）0 包。

两种可能：
1. **旧 DLL 时 `is_connected_` 确实变 true 了** → server 回的 ACK ssrc 匹配了 local SSRC
2. **旧 DLL 有不同的编译参数**

旧 DLL 编译时间 Jul 4 10:13（我没改过 RTPTransport.cpp），新 DLL 编译时间 Jul 5 21:16（改了 doProcessSocketData 加 log）。

**唯一变量是 `doProcessSocketData` 里的 `[XK_RTP]` log 代码。** 代码逻辑没变，只加了 printf。

**等等——旧 DLL 能收到 audio 说明 `is_connected_` 变 true 了！** 那 `processRtcpAppPacket` 的 AND 条件是满足的。

**但新 DLL 后 audio 也收不到了。** 这意味着新 DLL 编译后行为变了——可能 `static int rtp_pkt_count` 在多线程环境下有问题？或者 `printf` 在 Windows DLL 中阻塞了？

### 5. 验证假设：printf 阻塞

Windows DLL 中 `printf` 到 stdout，如果 Python 进程的 stdout 是 console（不是 terminal），`printf` 可能阻塞。如果 `doProcessSocketData` 在 UDP 接收线程调用，`printf` 阻塞会导致后续包被丢弃。

**但旧 DLL 的 PacedSender 也有 printf（[XK_PACED]），那个没阻塞。** 而且 RTPTransport 的 `doProcessSocketData` 只在 pull 端调用，PacedSender 在 push 端调用（Linux .so）。

## 明天的测试计划

### Step 1: 确认新 DLL printf 是否阻塞

用 `OutputDebugStringA` 替代 `printf`（Windows 原生 debug 输出，不阻塞）：

```cpp
#ifdef _WIN32
char buf[256];
snprintf(buf, sizeof(buf), "[XK_RTP] pkt #%d pt=%d\n", ...);
OutputDebugStringA(buf);
#else
printf("[XK_RTP] pkt #%d pt=%d\n", ...);
#endif
```

### Step 2: 如果 printf 不是问题

在 `processRtcpAppPacket` 加 `[XK_APP]` log（已加），看 ACK 包的 ssrc 值。确认：
- server 回的 ssrc 是 push 端的还是 pull 端的
- `audio_is_connected` 和 `video_is_connected` 是否都变 true

### Step 3: 如果 is_connected_ 是 true 但 video 还是 0

问题在 `VideoRTPReceiver::IncomingPacket` → `RtpDepacketizer::Parse` → `receiver_->InsertPacket` → `GetOrderedVideoPacketLoop`。

可能 H.264 depacketizer 解析失败（NAL type / FU-A 分片问题）。
