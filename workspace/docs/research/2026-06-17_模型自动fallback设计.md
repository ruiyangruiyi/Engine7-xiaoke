# 模型自动 Fallback 设计

## 背景
GLM 5.1 每天 10-11 点限流（[1305]），需要手动切 DeepSeek。潘总演示时全靠手动切扛住的。需要自动化。

## 当前架构分析

### 调用链
```
QueryEngine.query() 
  → this.provider.streamChat({ model, messages, ... })
    → OpenAIProvider.streamChat()
      → fetchWithRetry(url, init)  // HTTP 级重试（429/529/500+）
        → fetch() → SSE stream
```

### 重试层次（现有）
1. **HTTP 级** (`withRetry.ts`): 429/529/500+ → 同一个 API 重试，最多 10 次
2. **Stream 级** (`query.ts:307-320`): SSE error chunk → 同一个 model 重试，最多 3 次
3. **空响应** (`query.ts:322-355`): API 返回空 → 重试 1 次

### 问题
- 三层重试都是对**同一个 provider + 同一个 model** 重试
- `[1305]` 限流期间，重试 10 次还是限流，浪费时间
- 没有切换到备用 provider/model 的机制

## 方案：FallbackProvider 包装器

### 设计
创建 `FallbackProvider`，包装多个 `{ provider, model }` 组合。内部按优先级尝试，失败自动切下一个。

```
FallbackProvider
  ├─ primary:    { OpenAIProvider, "glm-5.1" }       (zhipu)
  ├─ fallback 1: { AnthropicProvider, "deepseek-v4-pro" } (deepseek)  
  └─ fallback 2: { OpenAIProvider, "qwen3.7-plus" }   (dashscope)
```

### 切换条件
- HTTP 429 / 529 → 立即切（不等重试）
- Stream error 含 `1305` / `overloaded` / `rate_limit` → 立即切
- 连接超时 → 重试 1 次同模型，再失败则切
- 普通错误（400/500 非限流）→ 不切，正常重试

### 配置格式（xiaoke.json）
```json
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "zhipu/glm-5.1",
        "fallback": [
          "deepseek/deepseek-v4-pro",
          "dashscope/qwen3.7-plus"
        ]
      }
    }
  }
}
```

### 不改的地方
- `QueryEngine` 不改 — 它调的 `provider.streamChat()` 接口不变
- `withRetry.ts` 不改 — HTTP 重试逻辑保留（同模型内的瞬时错误仍重试）
- `OpenAIProvider` / `AnthropicProvider` 不改

### 新增文件
- `src/models/fallback-provider.ts` — FallbackProvider 类

### 改动文件
- `src/models/provider-factory.ts` — 读 fallback 配置，创建 FallbackProvider
- `src/config/loader.ts` — 解析 `model.fallback` 配置

### FallbackProvider 核心逻辑
```typescript
async *streamChat(params) {
  for (const { provider, model, label } of this.chain) {
    try {
      // 用当前 provider+model 调用
      yield* this.tryProvider(provider, model, params)
      return  // 成功则结束
    } catch (fallbackError) {
      if (!shouldFallback(fallbackError)) throw fallbackError
      yield { type: 'status', text: `🔄 ${label} 限流，切换到下一个模型...` }
      continue  // 切下一个
    }
  }
  // 全部 fallback 都失败 → 抛最后一个错误
  throw lastError
}
```

### 关键决策点
1. **Fallback 触发时机**：provider-factory 创建时就组装好链，运行时按序尝试
2. **部分输出后失败**：如果 primary 已经 yield 了一些 text chunks 然后报错 → 不能切（上下文已脏），只能重试同模型。只有**连接阶段/第一个 chunk 之前**的失败才切
3. **日志可见**：切换时 yield status chunk，用户能看到 "🔄 GLM 限流，切换到 DeepSeek..."

## 冷静期策略（核心设计点）

**OpenClaw 缺的不是 fallback，是冷静期。** 当 GLM 1305 → 切 DeepSeek 后，下一次请求不应该立刻回切 GLM。

### 冷静期实现

每个 provider+model 组合维护一个 `cooldownUntil` 时间戳：

```typescript
type ChainEntry = {
  provider: LLMProvider
  model: string
  label: string
  cooldownUntil: number  // ms timestamp, 0 = 可用
}

class FallbackProvider {
  private chain: ChainEntry[]
  private readonly COOLDOWN_MS = 5 * 60 * 1000  // 5分钟冷静期
  
  async *streamChat(params) {
    for (const entry of this.getAvailableChain()) {
      try {
        yield* this.tryProvider(entry, params)
        return
      } catch (err) {
        if (shouldFallback(err)) {
          // 标记这个 model 进入冷静期
          entry.cooldownUntil = Date.now() + this.COOLDOWN_MS
          yield { type: 'status', text: `🔄 ${entry.label} 限流，冷却5min，切到下一个` }
        } else {
          throw err  // 非限流错误，不切
        }
      }
    }
    throw new Error('All models in fallback chain failed')
  }
  
  private getAvailableChain(): ChainEntry[] {
    const now = Date.now()
    // 过滤掉还在冷静期的
    return this.chain.filter(e => e.cooldownUntil <= now)
  }
}
```

### 冷静期长度

- 5 分钟（默认，可配）— 跟 GLM 1305 burst 模式经验值匹配
- 长限流时段（每天10-11点）— 5min 内会反复触发，进冷却后再回切，循环往复
- **更好的策略：** 指数退避 — 第一次冷却 5min，第二次冷却 10min，第三次 20min，最多 1h

### 部分输出保护

- 如果 primary 已经 yield 了一些 text chunks 然后报错 → **不能切**（上下文已脏），只能重试同模型
- 只有**连接阶段/第一个 chunk 之前**的失败才切
- 实现：记录 `hasYieldedText` 标志，true 时不切

### 配置格式（xiaoke.json）

```json
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "zhipu/glm-5.1",
        "fallbacks": [
          "deepseek/deepseek-v4-pro",
          "dashscope/qwen3.7-plus"
        ],
        "cooldownMs": 300000
      }
    }
  }
}
```

## 工作量评估
- FallbackProvider: ~150 行（含冷静期状态管理）
- provider-factory 改动: ~40 行  
- config loader 改动: ~15 行
- 测试验证: 手动模拟 1305

## 风险
- 不同模型的 tool_call 格式可能有差异（GLM vs DeepSeek vs Qwen）
- 需要确认 DeepSeek 和 Qwen 的 function calling 格式兼容
- **状态持久化：** 进程重启后冷静期状态丢失（影响不大，因为重启本来就该从头来）
