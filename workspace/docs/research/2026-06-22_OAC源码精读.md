# OAC (OpenAvatarChat) 源码精读

> 日期：2026-06-22 | 作者：小柯 | 目的：为 OAC 嵌入 engine 方案提供依据

## 1. 整体架构

OAC 是 Python 项目，核心是 **ChatEngine + Handler 管道**。

```
浏览器 ←WebRTC→ OAC 后端（ChatEngine）
                    │
                    ├── VAD Handler（语音活动检测）
                    ├── ASR Handler（音频→文字）
                    ├── LLM Handler / ChatAgent Handler（文字→回复）
                    ├── TTS Handler（文字→音频）
                    ├── Avatar Handler（音频→嘴型视频帧）
                    ├── Perception Handler（摄像头→视觉理解）
                    └── Client Handler（WebRTC/WS 连接管理）
```

Handler 之间**不直接调用**，通过 **DataSink 订阅机制**（`chat_session.py:267-270`）：
- 每个 handler 声明 `inputs`/`outputs` 数据类型
- 引擎自动把 output 类型路由到订阅了该 input 类型的 handler
- 像电路里的信号总线，handler 是组件，ChatDataType 是引脚

## 2. 音频链路（完整数据流）

```
mic float32[1,N] 16kHz
    │
    ▼
DuplexVAD (duplex_vad_handler.py:96-110)
    │ 切片 1024~clip_size 样本，Silero 状态机 START→POST_END
    │ 输出: HUMAN_DUPLEX_AUDIO + human_speech_start/end 标志
    ▼
ASR SenseVoice (asr_handler_sensevoice.py:72-84)
    │ 累积音频到 is_last_data，一次性 model.generate() 输出整段文本
    │ 输出: HUMAN_TEXT
    ▼
ChatAgent (chat_agent_handler.py:365-385) 或 SimpleLLM
    │ Agent Loop: tool_use → execute → feedback → repeat (最多5轮)
    │ 流式输出 token
    │ 输出: AVATAR_TEXT
    ▼
TTS CosyVoice (tts_handler_cosyvoice.py:94-107)
    │ 按标点分句 → 多进程推理 → 24kHz 音频
    │ 输出: AVATAR_AUDIO
    ▼
Avatar MuseTalk (avatar_handler_musetalk.py:325-348)
    │ 音频驱动嘴型同步 → 视频帧
    │ 输出: AVATAR_VIDEO (+ AVATAR_AUDIO 透传)
    │ ⚠️ 强约束: 输出帧率必须 == RtcClient.output_video_fps
    ▼
WebRTC → 浏览器播放
```

**关键发现：SenseVoice ASR 是非流式的**——必须等 VAD 确认说完才整段推理。不是 paraformer-zh-streaming 的流式。这跟翀哥之前说的"paraformer 65ms"不一样——65ms 可能是指推理速度，但 VAD 等 2s 端点检测才是真瓶颈。

## 3. 视觉链路

```
camera [H,W,3] 30fps
    │
    ▼
PerceptionHandler (perception_handler.py:237-253)
    │ 每 key_frame_interval(默认10) 抽帧到 buffer
    │ 每 summary_interval(默认3-5s) 提交异步任务
    │ max 3 并发
    ▼
OpenAIVisionModel (qwen3-vl-flash)
    │ 生成结构化 PerceptionData:
    │   - scene_summary（场景描述）
    │   - user_state（用户状态）
    │   - detected_events（检测到的事件）
    │
    ├─→ PERCEPTION_CONTEXT (JSON, 持续环境状态)
    └─→ ENVIRONMENT_EVENT (waving/showing_object/arriving, 5s去重)
    │
    ▼
ChatAgent._build_prompt_input()
    │ scene_summary → L3 environment_state
    │ recent_events → 离散事件嵌入 prompt
```

**视觉是异步的，不阻塞对话**。Perception 跑在旁边，有结果就注入下一轮 prompt，没有就跳过。

## 4. Avatar 渲染

MuseTalk 方案（`avatar_handler_musetalk.py`）：
- 音频驱动嘴型同步
- batch 推理，GPU ~30-50ms/帧
- **强约束**：输出帧率必须 == WebRTC output fps（否则 sys.exit！）
- H.264 硬编码：优先 nvenc/qsv，回退 libx264 ultrafast zerolatency

LiteAvatar 是另一种方案（`liteavatar_worker.py`），更轻量。

## 5. WebRTC 信令

基于 **fastrtc.Stream**（`client_handler_rtc.py:407-414`）：
- `modality="audio-video"`, `mode="send-receive"`
- FastAPI mount 的 Stream endpoint
- 浏览器 → FastAPI → RtcStream handler → 创建 session

**入向**（`client_handler_rtc.py:264-268`）：
- mic float32 `[1,N]` → `MIC_AUDIO`
- 视频帧 `[H,W,C]` → `CAMERA_VIDEO`
- 文本 → `HUMAN_TEXT`（datachannel）

**出向**（`client_handler_rtc.py:532-574`）：
- `AVATAR_AUDIO/VIDEO` → output_queues → RtcStream 推送
- `AVATAR_TEXT` → chat_channel（datachannel）

## 6. Agent + OC Bridge（关键发现）

OAC 有两条 LLM 路径：

### 路径 A：SimpleLLM（`llm_handler_openai_compatible.py`）
- 直连 OpenAI 兼容 API
- 无工具、无记忆、无 agent loop
- 简单的 `HUMAN_TEXT → AVATAR_TEXT` 管道

### 路径 B：ChatAgent（`chat_agent_handler.py`）
- **统一主 Agent**，合并了原 Manager + Persona
- 4 层 Prompt 编译（`prompt_compiler.py`）：L1 Core + L2 Persona + L3 Env + L4 Dialogue
- Agent Loop：`tool_use → execute → feedback → repeat`（最多 5 轮）
- 分层记忆（SessionMemoryManager）
- 主动触发（事件驱动 + 空闲驱动 + 待确认提醒）

### OC Bridge —— **已经在和外部引擎通信**！

这是我们方案最关键的发现。OAC 已经有一套完整的 OpenClaw Bridge：

| 组件 | 文件 | 作用 |
|------|------|------|
| **OcChannelClient** | `oc_channel_client.py` | HTTP webhook 双向通道。OAC → `POST localhost:18789/webhook/oac-bridge`；OC → `POST :8011/oc-reply` |
| **OcMcpClient** | `oc_bridge_init.py:68-97` | MCP 工具服务。启动 `node plugin-tools-serve.js`，注册 OC 工具 |
| **PersonaSnapshotManager** | `persona_snapshot_mgr.py:35-38` | 从 OC 拉 SOUL.md/IDENTITY.md 作人格 |
| **TaskNotificationQueue** | `task_notification_queue.py` | OC 后台任务结果注入 |
| **MemoryRetriever** | `memory_retriever.py` | 调 OC 的 memory_search |

**这意味着：OAC 已经设计好了和外部引擎集成的桥！** 我们的引擎（OpenClaw）已经有 `:18789` 端口——**OAC 的 OcChannelClient 可能直接就能接上**。

## 7. Handler 接口

基类 `HandlerBase`（`handler_base.py:16-62`）：

```python
class HandlerBase:
    async def load(self)                          # 加载模型/资源
    async def create_context(self)                # 创建会话上下文
    async def start_context(self)                 # 启动会话
    def get_handler_detail(self)                  # 声明 inputs/outputs 类型
    async def handle(self, data)                  # 处理数据（核心）
    async def destroy_context(self)               # 销毁会话
    # 可选: on_signal, on_before_register, on_setup_app
```

**Handler 间通信**：
- **数据**：`context.submit_data(data, finish_stream=...)` → 按类型分发到订阅队列
- **信号**：`context.emit_signal(ChatSignal)` → 按 SignalFilterRule 路由（STREAM_CANCEL/STREAM_END/SEMANTIC_WAIT）

## 8. 配置体系

YAML 配置（`config/*.yaml`），三段：`logger`/`service`/`chat_engine`。

```yaml
chat_engine:
  handler_configs:
    asr:
      module: handlers.asr.sensevoice  # 导入路径
      input_type_override: HUMAN_DUPLEX_AUDIO  # 替换默认输入类型
    llm:
      module: handlers.llm.openai_compatible
    tts:
      module: handlers.tts.cosyvoice
```

**handler chain 靠"输出类型 → 输入类型"隐式订阅连接**，无显式拓扑声明。`input_type_override`/`output_type_override` 允许复用同一 handler 但替换数据类型——这是全双工复用 ASR/EOU 的核心。

## 9. 延迟分析

| 环节 | 延迟 | 说明 |
|------|------|------|
| **VAD 端点检测** | **~2s** | `end_delay`=32000 样本（2s 静音确认）—— **最大瓶颈** |
| ASR 推理 | 65ms-200ms | SenseVoice 非流式，整段推理 |
| LLM 首 token | 300-800ms | qwen-plus 流式；ChatAgent 有 PromptCompiler + Agent Loop 开销 |
| TTS 首句 | 200-500ms | 必须等标点切句才提交 |
| MuseTalk | 30-50ms/帧 | GPU batch 推理 |
| WebRTC 编码 | ~10ms/帧 | H264 ultrafast |
| **全链路首字** | **~3-4s** | VAD 2s + ASR/LLM/TTS ~1-2s |

**优化空间**：
1. VAD end_delay 2s → SmartTurnEOU + SemanticTurnDetector 协作提前预测（已有）
2. ASR 换流式（paraformer-zh-streaming）→ 省 VAD 确认延迟
3. TTS 集成 token_buffer（`token_buffer.py` 有 SentenceAwareTokenBuffer 但 CosyVoice handler 未集成）

**视觉链路异步，非延迟瓶颈。**

## 10. 和我们引擎的接口点

OAC 有 3 种方式接外部引擎：

### 方式 A：用 OC Bridge（已有！）
- OcChannelClient 通过 HTTP webhook 双向通信
- OAC → `POST :18789/webhook/oac-bridge`（我们引擎加一个 webhook endpoint）
- 引擎 → `POST :8011/oc-reply`（OAC 的 callback server）
- **最快落地路径——引擎只需加一个 webhook handler**

### 方式 B：替换 LLM Handler
- 写一个新的 `llm_handler_engine.py`（类似 `llm_handler_openai_compatible.py`）
- OAC 内部调引擎的 HTTP API
- 保留 OAC 的 VAD/ASR/TTS/Avatar 全链路

### 方式 C：做成引擎的 Channel
- 引擎新增 `OacChannel`（类似 Discord/飞书 adapter）
- 引擎管 LLM，OAC 管 ASR/TTS/Avatar
- 两条管道通过 HTTP/WS 通信

**方式 A 是最优路径**——OAC 已经写好了 OC Bridge，我们引擎只需加一个 webhook endpoint。不需要写新 handler，不需要改 OAC 源码。
