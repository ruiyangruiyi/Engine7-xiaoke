# Carpo 视频通路排查

**日期：** 2026-07-05
**状态：** 进行中

## 问题

push H.264 60+ 包成功（ret=0），但 pull 端 0 收到。Audio 能转发，Video 不能。

## 根因定位

### tcpdump 证据
- Audio push：200 个 UDP 包到达北京 server ✅
- Video push：**0 个 UDP 包到达** ❌

### strace 证据
- Video push：247 个 sendto 到 23800，但**全是 8 字节（RTCP 信令）**
- **0 个视频 RTP 包（>8 bytes）发到 server**
- Audio push：499 个 sendto，大量 ~130 bytes Opus RTP 包正常发出

### 结论：PacedSender ForwardLoop 没有真正发送视频包

## 架构分析

### 音视频发送路径差异（RTPTransport::forwardMediaPacket line 203-234）

```cpp
if (type == pkt_video) {
    // Video: 走 PacedSender 队列
    paced_sender_->EnqueuePacket((char *)node.rtp, node.lenth);
} else {
    // Audio: 直接发
    packet_sender_->SendPacket(node.rtp, node.lenth, CP_UDP_TYPE_RTP_AUDIO);
}
```

**Audio 直接发，Video 走 PacedSender 队列。** 这是为什么 audio 正常但 video 卡住。

### PacedSender 架构（fengteng 2020/4/12 编写）

```
EnqueuePacket → packet_queue_ (FIFO)
                    ↓
ForwardLoop (后台线程):
  GetPendingPacket() → packet_sender_->SendPacket() → ProbeSent() → wait_until(NextProbeTime)
```

- ForwardLoop 是独立线程，构造时启动（line 26: `new std::thread(&PacedSender::ForwardLoop, this)`）
- 队列超 200 包或 10 秒数据会清空（ClearQueueIfOverhead）

### BitrateProber 状态

```cpp
BitrateProber::BitrateProber() {
    probing_state_ = ProbingState::kDisabled;  // 初始 disabled
    send_bitrate_bps_ = kDefaultSendBitrate_bps;  // 2048000 (2Mbps)
}
```

**但 ForwardLoop 不检查 probing_state！** 直接用 `send_bitrate_bps_` 算发送间隔：
```cpp
// CalculateNextProbeTime
int delta_ms = (sent_bytes_ * 8.0f / send_bitrate_bps_) * 1000.0;
return started_at_ + std::chrono::milliseconds(delta_ms);
```

### PacedSender 激活路径

**唯一激活方式：** `SetPacingRates(bitrate)` → `ResetProber(bitrate)`

调用链：
```
CongestionController::OnNetworkChanged(bitrate)
  → RTPTransport::onBandwidthChanged(bitrate)
    → paced_sender_->SetPacingRates(bitrate)
```

**OnNetworkChanged 的触发路径：**

1. **CongestionController 构造时** — `SetBitrates(300000, min, max)` 触发一次 `OnNetworkChanged(300000)`
   - 这是**初始激活**，PacedSender 拿到 300kbps × 3 = 900kbps pacing rate
   - 发生在 push 连接之前

2. **收到 RTCP ReceiverReport** — server 回传 RR，CongestionController 更新带宽估算
   - 需要服务器和 pull 端配合
   - 在纯 push 测试中可能不走这条路径

3. **收到 RTCP REMB** — 类似 RR

**注意：** `initSbeBitrate`（用户调 `setVideoBr` 时）**不触发** `OnNetworkChanged`——它只调 `SetSendBitrate` + `SetMinMaxBitrate`，不会回调。

### Android/iOS push 流程（无额外 pacing 初始化）

```
getNewPushSender → setSSRC → setVideoBr → setRtcServerAddr → startPush → sendMediaData
```

Android `LocalUser.java` 和 iOS `LovePeaLive` 在 startPush 之后**没有任何额外的 pacing 初始化调用**。

push 连接 ACK（`processRtcpAppPacket` 的 `kaskPublish`）后只启动 `kTimerSenderReport`（每200ms发SR），**没有启动 pacing 相关定时器**。

### PyAV H.264 格式（已排除）

PyAV x264 输出：SPS (nal_type=7) + PPS (8) + IDR (5) + P (1)，起始码 `00 00 00 01` ✓。`getH264PayloadType` 和 `skipNalStartCode` 能正确识别。

## 已排除

| 假设 | 结论 |
|------|------|
| Pusher A/V 同步阻塞 | ❌ 不存在，纯视频也能发 |

| PacedSender 队列溢出 | ❌ 60 包远小于 200 阈值 |
