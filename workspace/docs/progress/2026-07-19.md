# 2026-07-19 progress

## 录制调试工具最终方案

**问题**：A-V 同步诊断需要能录下 pull 端和 emit 端对比，但 fastrtc emit() 返回时丢失了 SDK 的 pts。

**今天的关键发现**：
1. **fastrtc audio track 永远用 `next_timestamp()` 自己算 pts，不用原始 SDK pts**（tracks.py:704-707）
   - 注释还自己写："Will probably have to give developer ability to set pts and time_base"
   - video track 在 send-receive 模式保留原始 frame.pts（tracks.py:202-209）
   - **这就是 audio/video 时间基错位的根因之一**

2. **实测数据（22:07）**：
   - **A-V pts diff (pull 端) = 280ms** — SDK pull 出来时 audio 已经比 video 慢 280ms
   - **A-V pts diff (emit 端) = 200ms** — emit 之后 diff 反而减少 80ms
   - **结论**：fastrtc emit 端 **没有** 让 audio 变慢，问题不在这里
   - **下一级嫌疑**：fastrtc tracks.py 赋 pts（audio 自算/video 保留）→ aiortc 编码打 RTP → 浏览器 jitter buffer

3. **方案演进**：
   - 方案 A: PyAV mux mkv 带 pts → PyAV API 坑多，pass
   - 方案 C: ffmpeg subprocess pipe BGR → 重编码 CPU 爆，翀哥一眼看出
   - **方案 B 终版**: 直接写原始 H.264 NAL bytes + Opus 解码 PCM wav → ffmpeg mux
     - video 零 CPU（直接写 NAL 不解不编）
     - audio 解码很轻
     - **录制 mp4 sync OK**（翀哥 20:39 确认"很同步"）
   - 但录制位置在 pull callback，只能反映 pull 端时序，**不能反映 emit 端**

4. **最终方案：内存 A-V pts diff**（不录文件，零开销）
   - audio queue 改 3 元组 `(chunk, decode_ts, sdk_pts_ms)`，把 SDK pts 带到 emit 端
   - audio emit 时算 `sdk_pts_ms - _carpo_video_pts_ms`
   - 存内存变量 `_last_av_pts_diff_ms`
   - 延迟面板新加一行 "A-V pts diff (emit)" 实时显示

## 下一级排查方向

emit → 浏览器链路细分（8 环）：
1. fastrtc emit 返回 PCM/ndarray
2. **fastrtc 赋 pts（audio 自算 next_timestamp / video 保留 frame.pts）← 关键嫌疑**
3. aiortc AudioStreamTrack/VideoStreamTrack
4. aiortc 编码 + 打 RTP
5. WebRTC 网络传输 + jitter buffer（Carpo 自研 PacedSender）
6. 浏览器 WebRTC stack 收 RTP → 解码
7. 浏览器 jitter buffer + 渲染队列
8. 浏览器播放/渲染

翀哥提出**放弃 fastrtc 直接用 aiortc**——评估可行：
- 信令接口：50 行（server 收 /offer 返 answer）
- AudioStreamTrack subclass：30 行（recv_frame 喂 PCM + pts）
- VideoStreamTrack subclass：30 行（recv 喂 ndarray + pts）
- 浏览器侧 JS 不变
- **核心收益**：audio/video pts 都自己赋（用 SDK timestamp），时间基统一
