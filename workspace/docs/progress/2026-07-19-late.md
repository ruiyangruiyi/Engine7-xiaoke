# 2026-07-19 (晚) progress — A/V 起点对齐闸门（emit 层）

## 关键发现

**fastrtc 的 audio pts 用累计 sample 数**（utils.py:249），**video pts 用 next_timestamp()**（tracks.py:705）。
**两边都不用 SDK 原始 timestamp**，各自本地时钟算，起点偏差永久锁死。

## 实测数据

- audio SDK 第一帧 pts=0，video SDK pts=1640ms（video 早到 1.6 秒）
- emit 端我们算 A-V pts diff：pull=280ms / emit=200ms（diff 不一致 + 浏览器观感 audio 慢）
- 翀哥判断："audio 慢是起点积累"——就是谁先到谁就用本地时间先推 pts

## 方案演进（一天三轮）

### 第 1 版：SDK pull 层丢 video
- 在 `_carpo_on_media` video 分支丢解码后的 frame
- 失败：`video_emit` 没被调用过（fastrtc 还没启动 emit loop），永远丢 0 帧

### 第 2 版：emit 层丢 video frame
- 在 `video_emit()` 入口判断 `_a_first_seen_ts`，未到返 black frame
- 失败：audio queue 第一帧到达时已经堆积了 1.6 秒的 audio chunk，emit 时**全部按 SDK pts 推**，vs video 一起放时 audio 还在追

### 第 3 版（当前）：`is_av_sync_base_ready()` emit 层闸门 ✅

翀哥的原始思路：
- video queue 有数据 → `has_video = True`
- audio queue 有数据 → `has_audio = True`
- 都 true → 放行；任一 false → 丢

实现：
- `is_av_sync_base_ready()` 函数返回：
  - 本地模式（avatar!=autodl）→ 始终 True（本地无 video 不挡 audio）
  - autodl 模式 → `_has_video and _has_audio`
- `video_emit()` 没 ready → 丢 frame 返 black + 计数
- `emit()` (audio) 没 ready → 丢 chunk 返 silence + 计数
- 两边都 ready → `_av_aligned = True`，永久放行

## 残留问题

**对齐后浏览器里 audio 还是感觉慢**——闸门只对齐了 emit 起点，但 fastrtc 内部 audio/video pts 各自本地时钟推算，**之后还会漂移**。

**另一个嫌疑（翀哥 23:14）**：audio pull 没做 NACK，丢包就 pts 空一段，audio 落后 video。
- video 有 NACK（PacedSender 之前发现的）
- audio pull 可能没 NACK 机制

**翀哥 23:33-23:35 进一步分析（关键）**：
- audio emit 两处返 `np.zeros(480)` silence（line 372 queue None + line 442 TimeoutError）
- **填充 silence 会被 NetEq 当真实包播放，真实 audio 到了只能排在后面 → audio 越积越后**
- 应该返 None，让 fastrtc 自己处理（不要擅自填充）
- 另：audio pull 没有 reorder，UDP 乱序到达直接 deliver

audio 端完整坑（五重打击）：
1. UDP 乱序到达
2. SDK pull callback 直接 deliver（不 reorder）
3. 没 NACK（丢包就空）
4. fastrtc 自算 pts（不用 SDK 时间戳）
5. emit 返 silence 填充 → NetEq 推 audio

正确解法（明天）：
- emit queue 空 / None 时**返 None 不填 silence**
- monkey-patch fastrtc utils.py:249，让 audio pts 用 SDK timestamp
- 或者 monkey-patch tracks.py:705 video pts 用 SDK timestamp
- 或者彻底重构 aiortc
- 加 audio NACK + reorder buffer（如果 SDK 支持）
