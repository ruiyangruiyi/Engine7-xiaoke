# API超时重试导致重复发送

## 问题

2026-06-16 EP02直播时暴露：GLM API限流(1305)→retry→重复发消息。

### 链路
```
用户发消息 → engine调GLM → API流式返回（部分文字已yield给下游发送）
→ API中途超时/限流 → streamError → retry（重新发整个请求）
→ 新response的文本又被yield → 下游又发一次
→ 用户收到重复消息（有时大量重复一起过来）
```

### 根因
`query.ts` 第285-288行：文本是流式yield的，部分文字已经发出去后才报错retry。retry成功后又发了一整条。

```
yield chunk  // ← 部分文字已发到Discord/飞书
→ 然后API超时 → retry → 整条重新发
```

## 方案

### A. Retry前撤销已发内容（复杂）
- 追踪已经yield的文本
- retry前通知下游"撤回刚才发的"
- 实现复杂，Discord可以edit/delete但微信不行

### B. 缓冲+原子发送（推荐）
- 流式文本先缓冲不立即发
- API完整成功后一次性发送
- 缺点：失去打字实时感（流式显示）

### C. 缓冲窗口+延迟发送（折中）
- 文本流式缓冲，设一个短窗口（如2秒）
- 窗口内API完成 → 一次性发
- 窗口内API报错 → 丢弃缓冲，retry，不发送旧内容
- 优点：用户几乎无感延迟，retry不会重复发

### D. 已发送标记（最简单）
- 第一条text chunk yield时设标记 `hasYieldedText = true`
- retry前检查：如果hasYieldedText，不retry直接报错
- 缺点：可能本来retry一次就能成功，但放弃了

## 代码位置
- `src/core/query.ts` L285-288 — text chunk yield
- `src/core/query.ts` L296-320 — stream error → retry逻辑
- 下游发送：dispatcher/handle-query收到yield后的发送逻辑

## 相关
- GLM API [1305] 限流是触发源，但根因是retry不感知已发内容
- 今天直播时大量重复消息就是这个机制导致的
