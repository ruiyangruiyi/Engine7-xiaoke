## 背景

翀哥 17:52 说："只先针对飞书这个通道的群聊，先不做 preview，把 preview 的 enable 在群聊的时候弄 false"

**核心思路**：
- preview 流式期间敏感词无法事后拦截（流式 chunk 跨边界匹配不到）
- 飞书群聊场景关掉 preview → LLM 回复走 `cm.send` 路径 → 在 `manager.ts:send` 入口统一拦截敏感词
- 之前回滚掉了 previewEnabled 配置 + StreamPreview enabledOverride

---

## 6/18 18:06 讨论进展（重要更新）

翀哥进一步指出：**`delivered=true` 也有问题**。

- `preview.finish()` L137-140 正常路径：`editPreview` 把 preview 改成最终内容（去蓝框）→ 返回 `delivered=true`
- 这个 preview **视觉上**是最终消息 → **人眼能看到**
- 但 preview 走 patch/edit 事件 → **姐姐 bot 监听不到**"消息创建"事件 → **bot 感知不到**
- 上午 12:02 姐姐没收到就是这个原因

**CC connect 的解法**：删 preview + 转普通消息发出（保证 bot 监听到）。代价是"呈现两次"。

**翀哥的判断**："呈现两次也没关系"——感知到比花哨重要。

---

## 18:09 最终方案（翀哥拍板）

**两个改动**：

1. **飞书群聊 preview 关闭**——StreamPreview 构造时判断，飞书群聊传 `enabled: false`
2. **onResult 强制 cm.send**——不管 `delivered` 是 true/false，都强制调 `cm.send` 一次

第二个改动是**核心修复**（让姐姐感知到回复），第一个改动是**配套**（preview 中间态完全消失，只剩最终消息）。

## 实施内容（方案 A：改 StreamPreview 构造）

**文件**：`src/engine-startup.ts` L1609-1615

**改动**：
```ts
const isFeishuGroup = inbound.channel === 'feishu' && /* 是群聊的判定 */

const previewConfig = isFeishuGroup
  ? { ...DEFAULT_PREVIEW_CONFIG, enabled: false }
  : DEFAULT_PREVIEW_CONFIG

const preview = new StreamPreview(previewConfig, ...)
```

`enabled=false` 时 StreamPreview 内部：
- `appendText` 直接 return → 不累积不发送
- `finish()` 看到 `previewHandle === null` → 返回 `false` → 上层 `cm.send`

**配合 onResult 强制 cm.send**：preview 不发 + delivered 必为 false + 强制 cm.send 一次 = 飞书群聊只走 cm.send 路径。

## 关键判断点

### 1. 飞书群聊怎么判定？
- `inbound.channel === 'feishu'`（通道名）
- `inbound.channel_id` 是否以 `oc_` 开头（飞书群聊 chat_id 格式）
- 或者 `inbound.from` 是否有 `chat_type === 'group'`

### 2. `delivered=true` 时的处理
- 当前逻辑：`delivered=true` 不再调 cm.send
- 新逻辑：**强制 cm.send**（不管 delivered 是 true/false）
- 配套：delivered=true 时 `preview.finish` 已经 `editPreview` 改成最终消息，cm.send 又发一次 → **视觉上两条**（preview + 普通消息）
- 翀哥确认："呈现两次也没关系"
