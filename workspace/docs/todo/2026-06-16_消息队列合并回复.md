# 消息队列合并回复 — 最终方案

## 状态

✅ 6/19 11:40 实施完成（d6636f6），6/19 13:00 翀哥验证通过（飞书+Discord 图片识别均正常）

## 核心决策

| 项目 | 决策 |
|------|------|
| **合并时机** | dispatcher 出队时合并（不用 debounce） |
| **合并 key** | `{channel}:{channel_id}:{from}` |
| **带图消息** | 也合并 |
| **文本拼接** | 不拼，每条消息保持独立 content block |
| **meta 位置** | 单独 text block，放最前面 |
| **JSONL** | 写的时候 image 抠掉，text join |
| **处理顺序** | 串行，不同 from 各自合并 |
| **callbacks** | 用第一条的 |

## 实现方案

### 1. handle-query.ts — 统一 content blocks

**现在：**
```ts
if (Array.isArray(text)) {
  userMsgContent = text  // blocks 原样传，不加 meta
} else {
  userMsgContent = formatWithMeta(text, ...)  // string 加 meta
}
```

**改成：**
```ts
// 统一转成 content blocks
const metaBlock = { type: 'text', text: formatMeta(inboundMeta, workspace) }
const contentBlocks = Array.isArray(text)
  ? [metaBlock, ...text]
  : [metaBlock, { type: 'text', text }]
userMsgContent = contentBlocks
```

**好处：**
- 去掉 if/else 分支，统一走 content blocks
- meta 永远是第一个 block
- 合并场景直接拼数组就行

### 2. message-queue.ts — 加 dequeueBatch 方法

```ts
dequeueBatch(sessionId: string, key: string): QueuedMessage[] {
  const batch: QueuedMessage[] = []
  for (let i = this.queue.length - 1; i >= 0; i--) {
    const msg = this.queue[i]!
    if (msg.sessionId !== sessionId) continue
    if (this.buildKey(msg) !== key) continue
    batch.unshift(this.queue.splice(i, 1)[0]!)
  }
  return batch
}

buildKey(msg: QueuedMessage): string {
  const channel = msg.channelName
  const channelId = msg.inboundMeta?.channel_id ?? ''
  const from = msg.inboundMeta?.from ?? ''
  return `${channel}:${channelId}:${from}`
}
```

### 3. message-dispatcher.ts — tryDispatch 改成合并

```ts
private tryDispatch(sessionId: string): void {
  const guard = this.getGuard(sessionId)
  if (guard.isActive) return
  if (!this.queue.hasSessionMessages(sessionId)) return

  const gen = guard.tryStart()
  if (gen === null) return

  // 取第一条，确定 key
  const first = this.queue.dequeue(sessionId)
  if (!first) {
    guard.cancelReservation()
    return
  }

  const key = this.queue.buildKey(first)
  // 扫队列同 key 的合并
  const rest = this.queue.dequeueBatch(sessionId, key)
  const batch = [first, ...rest]

  // 合并 content blocks
  const combined = this.combineMessages(batch)

  this.executeMessage(combined, gen)
}

private combineMessages(batch: QueuedMessage[]): QueuedMessage {
  const first = batch[0]!
  const metaBlock = { type: 'text', text: this.formatMeta(first.inboundMeta) }
  const contentBlocks: ContentBlock[] = [metaBlock]

  for (const msg of batch) {
    if (typeof msg.text === 'string') {
      contentBlocks.push({ type: 'text', text: msg.text })
    } else {
      contentBlocks.push(...msg.text)
    }
  }

  return {
    ...first,
    text: contentBlocks,
  }
}
```

### 4. JSONL 写入

handle-query.ts 里 writer.writeUserMessage 时，从 content blocks 提取所有 text block join：

```ts
const textForJsonl = contentBlocks
  .filter(b => b.type === 'text')
  .map(b => b.text)
  .join('\n')
writer.writeUserMessage(textForJsonl)
```

## 不合并的情况

- cron/heartbeat/system 消息（source !== 'user'）
- 不同 from
- 不同 channel
- 不同 channel_id（DM vs 群聊）

## 实现结果（6/19）

### 改了什么

| 文件 | 改动 |
|------|------|
| `handle-query.ts` | 统一 content blocks 路径：meta 单独 text block 放最前面，后面是原始内容（string 或 ContentBlock[]）。JSONL 写入时 image 抠掉，text join，末尾追加 `[图片×N]` |
| `message-queue.ts` | 加 `buildKey()`（构造合并 key）+ `dequeueBatch()`（批量出队同 key 消息）。`source !== 'user'` 的消息不参与合并 |
| `message-dispatcher.ts` | `tryDispatch` 出队第一条后扫队列同 key 合并。`combineMessages` 把所有消息的 content blocks 平铺到一个数组 |

### 数据流

```
飞书/Discord 发图
  → channel handler 构造 ContentBlock[]（text + image blocks 已在同一数组）
  → submitMessage({ text: ContentBlock[], source: 'user' })
  → queue.enqueue()
  → tryDispatch()
    → dequeue 第一条
    → dequeueBatch 扫同 key（同 channel + 同 channel_id + 同 from）
    → combineMessages：所有 messages 的 blocks 平铺合并
    → executeMessage(combined)
      → handle-query 检查 content blocks 是否有 image
        → 有 image → visionDeps（vision 模型，如 qwen3.7-plus）
        → 无 image → 主 deps（文本模型，如 qwen3.7-max）
      → LLM 调用
```

### 与 openclaw 方案的差异

| 维度 | openclaw | Engine 实现 |
|------|----------|-------------|
| **合并时机** | debounce（时间窗口，默认 800ms） | 出队时合并（guard busy 期间积压的同源消息） |
| **带图消息** | 不参与合并（`hasMedia → false`） | **参与合并**，image blocks 平铺进 content blocks |
| **文本拼接** | `\n` join 成一条字符串 | **不拼**，每条保持独立 content block |
| **合并 key** | `{channel}:{accountId}:{channelId}:{authorId}` | `{channel}:{channel_id}:{from}` |

### 选择出队合并而非 debounce 的原因

- Engine 用 QueryGuard 串行控制，guard busy 时新消息自然积压在队列里
- 出队时一次性取同 key 的全部消息，不需要额外的定时器
- 比 debounce 简单，不需要管理 timeout/cancel 逻辑

## 架构决策：Vision 路由（6/19 翀哥确认）

### 问题

batch 里带图片时，是整条消息走 vision 模型，还是文本和图片分开走不同模型？

### 决策

**整条消息走一个模型。** 扫描 content blocks，只要有任何一个 image block → 整个 batch 走 vision 模型。

### 实现

```typescript
// engine-startup.ts L1744-1746
const hasImages = Array.isArray(queryContent) && queryContent.some(b => isImageBlock(b))
const msgDeps = (hasImages && visionDeps) ? visionDeps : deps
```

- **有图** → `visionDeps`（vision 模型，如 `dashscope/qwen3.7-plus`，`modelInputs: ['text', 'image']`）
- **无图** → 主 `deps`（文本模型，如 `dashscope/qwen3.7-max`，`modelInputs: ['text']`）

### 为什么不分模型

- vision 模型也能处理文本，所以带图的 batch 全部丢给 vision 模型没问题
- 不存在"文本走一个模型、图片走另一个"的情况
- 一条消息只走一个模型，保持上下文一致性

### 模型不支持图片时的处理

```typescript
// handle-query.ts L208-233
const supportsImages = modelInputs.includes('image')
if (!supportsImages) {
  // 把 content blocks 里的 image block 全剥掉，只留文本
  // 如果剥完空了，替换为 '[image]' 占位
}
```

这是兜底逻辑：如果因为某种原因（如 /model 手动切到纯文本模型），image blocks 会被过滤掉，不会导致 API 报错。
